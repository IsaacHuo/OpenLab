# OpenLab
## 开放式科研操作系统：产品愿景与总体战略规划

**OpenLab — The Open Research Operating System**

**项目性质：** 完全开源、开放生态、本地优先、跨学科、可扩展  
**核心定位：** 全球开源科研工具、AI Agent、学术知识、科学数据与计算能力的统一集成平台。

---

# 一、愿景：重新组织个人与世界的科研能力

OpenLab 的长期愿景，是让任何拥有普通计算机的人，都能够利用全球已有的开源科研基础设施，独立开展过去往往需要专业研究团队才能完成的复杂研究工作。

现代科学研究存在一个结构性问题：

全球不断出现优秀的开源项目、算法、科研 Agent、实验工具、数据集和学术资源，但这些能力高度分散。

研究者必须自行寻找工具、理解技术栈、解决环境依赖、配置模型、组织数据，并协调不同软件之间的工作。

大量科研时间消耗在工具本身，而非研究问题。

OpenLab 希望建立一个统一的科研环境，将这些分散的能力组织成可以发现、调用、组合、复用和持续演化的系统。

它不仅服务于计算机科学，也面向经济学、社会科学、数学、统计学、语言学、历史学、数字人文、管理学、计算生物学以及各类计算驱动的交叉学科。

平台重点支持能够利用公开文献、数据、算法、计算实验、数值仿真和理论分析完成的研究。

对于需要真实物理实验、临床实践或线下调查的研究，OpenLab 可以承担辅助分析角色，但不应宣称能够替代现实世界的实证工作。

**最终目标：让科研能力像软件组件一样被组织，让科研过程像计算工作流一样被执行，让科研成果像开源代码一样可以被验证、复现和继承。**

# 二、产品定位：从工具聚合到科研基础设施

OpenLab 不应被简单定义为 AI 聊天应用、论文生成器、GitHub 仓库集合或 Agent 框架。

这些只是它可能提供的局部能力。

更准确地说，OpenLab 同时承担五种角色。

### 1. Research Workspace：科研工作空间

统一组织研究课题、文献、数据、实验、代码、图表、论文和研究历史。

研究项目是平台最重要的长期资产，不应该依附于某个特定模型或工具。

### 2. Research Marketplace：科研能力市场

汇聚全球现有的开源科研工具。

支持用户发现、安装、管理和更新各种 Skills、MCP 服务、科学计算工具、科研 Agent 和完整科研系统。

### 3. Research Orchestrator：科研协作与调度中心

负责将不同来源的科研工具组织成完整研究流程。

允许多个 Agent、工具和计算任务协作，并允许研究者随时介入、修改或停止流程。

### 4. Research Intelligence：科研发现与知识组织中心

连接学术论文、引用网络、开放数据、代码仓库与研究成果，帮助用户了解一个领域的发展现状、重要争议、研究空白和潜在突破方向。

### 5. Research Infrastructure：开放科研基础设施

提供可复现执行、计算资源管理、科研成果追溯、插件标准和开放扩展能力。

这五种角色共同组成 OpenLab，而非五个互不关联的产品。

# 三、核心架构：一个平台连接多种科研世界

OpenLab 应采用开放、模块化、可替换的总体架构。

这里的架构划分是功能边界，而非规定必须采用多少进程、服务或代码仓库。

## 1. Experience Layer — 用户交互层

负责人与科研系统之间的所有交互。

长期支持不同的使用形式：

- Web Research Workspace：浏览器科研工作台。
- Desktop Experience：可选的桌面客户端。
- CLI：面向开发者和高级研究者的命令行界面。
- Programmatic API：允许其他软件调用 OpenLab。
- Agent Interface：允许外部 AI Agent 将 OpenLab 作为科研能力提供者。

初期可以采用本地启动、浏览器访问的形式，但产品架构不应与某一种交互方式绑定。

同样的研究项目和工具能力，应当能够通过不同客户端访问。

## 2. Control Plane — 平台控制层

这是整个系统的管理中心。

负责统一管理科研项目、科研工具、执行任务、AI 模型、资源限制、权限策略、运行状态和工作流。

Control Plane 不必亲自执行所有科研工作。

它主要回答：

谁在执行任务？使用什么工具？访问哪些资源？当前处于什么状态？结果保存在哪里？是否允许继续执行？

这种职责分离能够支持未来接入越来越多的第三方科研系统，而不必不断修改平台核心。

## 3. Integration Layer — 开放集成层

这是 OpenLab 最核心的技术竞争力。

开源科研项目的架构可能完全不同。平台不应要求开发者按照 OpenLab 的内部代码结构重新实现现有项目。

应建立统一的集成规范，通过 Adapter 将不同能力接入平台。

长期支持以下类别：

**Skills**

以 Agent Skills 等开放规范为基础，接入结构化提示词、科研方法论和专用 AI 技能。

**Tools**

支持 Python、R、Julia、CLI、可调用软件包以及各类传统科学计算程序。

**Services**

支持 MCP、HTTP API 和其他标准化服务接口。

**Agent Systems**

接入 OpenCode 类 Agent Runtime、科研专用 Agent 和多智能体系统。

**Research Engines**

接入 AI Scientist、RD-Agent 等拥有独立任务流程和执行环境的完整科研系统。

**Data Providers**

整合学术文献数据库、科学数据集、科研知识图谱和其他开放数据服务。

OpenLab 应尽可能直接兼容成熟标准，在必要时提供适配机制。

它的职责是连接现有生态，而不是为整个科研行业再创造一套封闭协议。

## 4. Execution Layer — 科研计算与执行层

负责真实运行科研任务。

应当同时考虑：

- 本地 CPU 与 GPU 计算。
- 独立 Python、R 等科学计算环境。
- 容器化科研软件。
- 外部模型和计算服务。
- 可选的远程计算资源。
- 长时间运行的实验任务。
- 批量实验和并行任务。
- 实验失败、重试、恢复及结果追踪。

重点是建立统一的执行管理能力。

不同工具可以继续使用自己的运行方式，只要能够向平台报告任务状态、接受必要控制，并以可识别的形式交付结果。

## 5. Research Data & Knowledge Layer — 科研数据与知识层

这一层管理平台最重要的长期资产。

包括文献、数据集、研究问题、假设、实验配置、代码、图表、运行记录、参考文献和研究结论。

需要建立跨工具共享的研究对象模型。

例如，一项实验不应该只是某个 Agent 输出的一段文字，而应包含它使用的数据、方法、参数、执行环境、输出文件、结果解释和已知局限。

应尽可能兼容 RO-Crate、科研引用格式和其他现有开放标准。

**工具可以不断更新、被替代甚至消失，研究成果及其来源不能因此丢失。**

## 6. Trust & Governance — 信任与治理体系

安全、科研诚信、许可合规和可复现性是贯穿整个架构的基本能力。

平台必须区分来自可信维护者的工具、社区贡献和未经验证的外部仓库。

用户可以自由探索开源生态，但系统不能默认允许未知代码访问所有本地文件、模型密钥和网络资源。

同时必须清楚区分：

已验证事实、模型推断、实验观察、待检验假设以及未经确认的研究结论。

不能通过 AI 自动生成文章，就宣称完成了科学发现。

# 四、第三方集成体系：OpenLab 的生态核心

第三方项目应当成为 OpenLab 的一等公民。

用户应能够通过工具市场、GitHub 地址或本地路径发现和安装科研能力。

平台自动识别项目类型、依赖、版本、许可证、运行环境和可提供的功能。

针对无法自动适配的项目，可以由社区提供专门 Adapter。

为避免“支持某个项目”这一说法过于模糊，应建立明确的集成成熟度：

**Level 0 — Discoverable**

平台能够发现项目、展示信息、说明用途与兼容性。

**Level 1 — Installable**

平台能够管理项目的安装、版本、依赖和卸载。

**Level 2 — Executable**

平台可以真正启动项目、传入任务并接收结果。

**Level 3 — Composable**

项目可以与其他科研工具交换结构化成果，参与统一工作流。

**Level 4 — Reproducible**

平台能够完整记录执行条件、版本和数据，使研究者能够独立验证和复现结果。

未来工具市场必须清晰展示集成等级。

不能将仅仅收录 GitHub 链接的工具称为已经完整集成。

## 首个标准集成：Supervisor-Skills

项目来源：

https://github.com/HKUSTDial/Supervisor-Skills

Supervisor-Skills 应成为 OpenLab 首批官方验证的集成案例之一，也是 Skill 集成标准的重要参考。

平台应能够识别它所包含的多个科研 Skills，保留其原始结构、参考资料和方法论，并通过用户选择的 Agent Runtime 执行。

从用户角度看，这些技能应表现为平台内置的科研能力。

例如：

研究构思评估、深度文献综述、论文写作、科研图表设计、投稿前审查等。

用户无需理解 `SKILL.md` 的技术细节，也不必亲自复制 Prompt。

平台同时应保留高级入口，允许研究者查看原始 Skill、调整参数、指定模型、控制可调用工具以及审查执行过程。

这一集成应当成为未来支持其他科研 Skills 仓库的通用基础，而不是只针对 Supervisor-Skills 编写一个特例。

同时必须保留第三方作者、来源、版本和许可证信息。OpenLab 完全开源，并不意味着所有第三方组件具有相同的再分发与商业使用权限。

# 五、用户体验：从研究问题出发，而非从软件出发

OpenLab 应允许不同经验层次的研究者使用同一套能力。

### 模式一：Goal-Driven Research

用户直接描述研究目标。

例如：

“我想研究大语言模型对不同国家劳动力市场的影响，希望使用公开数据进行统计分析。”

平台帮助用户识别所需文献、数据、方法和工具，提出可执行的研究计划。

计划经用户确认后，再调用相应科研能力。

### 模式二：Tool-Driven Research

高级用户可以直接指定工具。

例如安装 Supervisor-Skills，选择 Idea Evaluator，配置模型并独立运行。

平台不应强制所有用户进入自动编排流程。

### 模式三：Workflow-Driven Research

用户能够将多个科研工具组合成完整流程。

例如：

Idea Evaluator → Deep Research → 文献核查 → 数据分析 → 实验评估 → Paper Writer → 独立审稿。

未来还应支持保存、分享和复用科研工作流，使其成为开放生态中的另一种标准化资源。

### 模式四：Exploratory Research

系统根据研究者关注的学科，持续整理值得关注的新论文、新工具、研究争议和潜在交叉学科问题。

它可以提出候选研究方向，但不能把自动推断的研究空白直接视为经过验证的创新点。

这四种模式应当共存，并共享同一套研究项目、数据和执行记录。

# 六、跨学科体系：以研究方法组织科学能力

OpenLab 应覆盖尽可能广泛的学科，但不能简单地将大学专业目录复制进产品。

更有价值的方式是建立两套相互关联的分类体系。

第一套是**学科知识分类**。

覆盖计算机、数学、经济学、社会学、语言学、历史学、管理学、数字人文、能源系统、生物信息学等领域，并允许社区持续扩展。

第二套是**科研方法分类**。

包括文献研究、计量分析、统计建模、机器学习、网络科学、文本分析、数值模拟、算法实验、形式化验证、系统综述和科学可视化。

这种双维度结构具有重要意义。

例如，网络科学既能研究互联网拓扑，也能研究学术合作、产业创新扩散和社会关系。

平台可以帮助用户发现不同学科之间共享的研究方法，推动现有工具跨领域复用。

长期还可以建立学科能力包（Discipline Packs），集合某一领域常用的数据源、方法规范、工具组合、实验模板和评价标准。

# 七、科研工作流与多 Agent 协作

OpenLab 不应内置一套不可替换的“超级科研 Agent”。

更合理的方向是建立一个能够管理不同 Agent、科研工具和计算任务的协调系统。

不同研究阶段可以采用不同的专业能力。

例如：

- 文献研究系统负责建立证据基础。
- 研究设计系统负责提出假设和实验方案。
- 计算工具负责执行数值分析和仿真。
- 统计审查系统负责检验结果的稳健性。
- 论文写作系统负责组织真实研究材料。
- 独立审查系统负责寻找方法缺陷和证据漏洞。

这些角色可以来自不同项目、不同模型、不同研究团队。

所有角色应通过明确的任务合同和结构化成果协作，避免完全依赖自然语言传递研究状态。

其中必须支持人工决策节点。

用户应当能够审查研究计划、批准资源消耗、修正假设、干预实验并拒绝不可信结论。

**自动化的目标是提升研究能力，而不是取消科学判断。**

# 八、开放生态与社区建设

OpenLab 的长期生命力取决于开放生态，而非核心团队能编写多少插件。

因此应建立面向第三方贡献者的开放集成体系。

开发者可以发布科研工具适配器、学科能力包、科研工作流和数据连接器。

研究者可以分享经过验证的计算实验模板、方法论和研究成果结构。

社区可以参与工具质量评估、兼容性维护、安全审查以及跨平台支持。

未来可以形成几类公开资源：

**OpenLab Registry**

开放的科研工具与适配器索引。

**OpenLab Workflows**

可复用的研究工作流库。

**OpenLab Research Packs**

按研究主题和学科组织的能力集合。

**OpenLab Benchmarks**

用于验证科研工具可靠性、可复现性和执行能力的标准任务。

**OpenLab SDK**

帮助开发者将新的科研工具接入平台。

平台的工具注册机制应尽可能开放，允许社区托管独立 Registry，避免科研生态依赖单一服务器。

OpenLab 核心代码与第三方资源保持独立许可证及贡献关系。

# 九、科研质量与可复现性

这是 OpenLab 长期区别于普通 AI 内容生成平台的重要能力。

科研系统应鼓励提出假设，但必须严格管理假设与证据之间的关系。

任何研究流程都应尽可能记录：

研究问题、资料来源、数据版本、使用方法、工具版本、模型配置、关键参数、实验结果、验证过程和已知局限。

平台需要支持独立审查、结果复现、失败记录以及负面结果归档。

研究失败不应被自动隐藏。

统计结果不显著、不支持原假设、无法复现或与既有文献冲突，都应作为合法的研究结果保存。

长期可以建立统一的 Research Provenance 体系，让用户追踪一张图、一段论文结论或一个实验指标究竟来自哪些原始资料与计算步骤。

对于科研论文生成，平台应遵守目标学术机构、期刊及会议关于 AI 辅助研究与写作的规定。

# 十、部署与可持续运行战略

OpenLab 坚持 Local-first，但不应被限定为只能在个人电脑上运行。

它应当拥有一致的逻辑架构，同时支持不同部署环境：

**Personal**

个人电脑、本地浏览器、本地数据与个人模型配置。

**Workstation**

具备更强 CPU、GPU 和存储能力的科研工作站。

**Remote Compute**

个人计算机管理任务，实际计算在远程服务器或其他授权资源上完成。

**Institutional**

未来供研究团队、实验室和机构使用的共享部署模式。

这些模式应尽可能共享核心功能和接口规范，而非发展成彼此割裂的独立产品。

平台应保留充分的离线能力，允许科研项目、数据与配置迁移，避免依赖单一云服务或模型供应商。

# 十一、长期发展战略

OpenLab 的发展不以固定日期或代码规模划分，而按平台能力成熟度推进。

### 第一阶段：统一科研入口

建立清晰的平台体验与开放集成机制。

使用户能够在同一科研空间中发现、安装、配置和调用不同类别的科研工具。

形成稳定的基础研究项目模型。

### 第二阶段：科研能力互联

让 Skills、科学计算工具、科研 Agent、学术数据库和完整科研引擎真正协作。

建立通用科研成果格式和可靠的跨工具任务流程。

### 第三阶段：计算科研操作系统

形成成熟的科研任务调度、计算资源管理、研究历史、成果追溯和复现体系。

让复杂计算研究可以长期运行、持续迭代。

### 第四阶段：跨学科科研网络

整合更多专业领域的研究方法、工具、数据和工作流。

建立学术知识关联体系，支持主动发现跨学科研究机会。

### 第五阶段：开放科研生态

让独立开发者、实验室和研究机构能够基于 OpenLab 发布科研能力。

推动科研工具之间形成更加广泛的互操作标准。

最终，OpenLab 不再依靠核心团队逐一维护全部科研工具，而由开放社区共同推动发展。

# 十二、成功标准与核心竞争力

衡量 OpenLab 的成功，不能只看 GitHub Stars、接入仓库数量或论文生成速度。

更重要的标准包括：

**可接入性**：第三方开发者能否以合理成本接入自己的科研工具。

**可组合性**：不同团队开发的科研软件能否真正协作。

**可执行性**：科研任务能否在符合条件的环境中稳定运行。

**可复现性**：研究者能否追踪和重现研究成果。

**开放性**：用户是否拥有自己的数据，是否能够自由替换模型与工具。

**科研价值**：平台是否真正减少重复劳动、提高研究质量、扩大个人可开展研究的范围。

OpenLab 的核心竞争力最终将来自三个长期积累的资产：

1. **广泛且可靠的科研软件兼容生态。**
2. **跨工具、跨学科的科研工作流与成果标准。**
3. **开放、可验证、可持续积累的科研知识与执行体系。**

# 十三、对未来开发 Agent 的最高指导原则

本规划描述的是 OpenLab 应成为怎样的产品和生态，不是对具体实现技术的强制规定。

执行 Agent 应当拥有充分的工程决策空间。

可以根据现有成熟开源项目、行业标准、维护成本和实际兼容性，选择复用、扩展、集成或自主开发。

但所有重大技术决策都必须服从以下原则：

- 避免重复建设成熟的开源科研能力。
- 优先兼容现有标准，降低第三方接入成本。
- 保持平台核心与外部工具解耦。
- 不将产品架构绑定于某一家模型供应商。
- 不因短期便利破坏长期可扩展性。
- 不为追求复杂而引入没有必要的基础设施。
- 不牺牲科研可信度来制造自动化演示。
- 以可持续维护、开放协作和真实科研价值作为最终判断标准。

允许架构持续演化，允许重大设计被推翻，允许替换最初选用的基础技术。

只要核心愿景不变，具体的实现方式就应保持开放。

# 结语

OpenLab 希望解决的，是未来科研领域一个基础性问题：

**当世界上已经存在大量优秀的科研软件、AI Agent、算法、模型和开放知识时，为什么个人研究者仍然需要独自承担寻找、安装、理解、连接和管理这些能力的全部成本？**

OpenLab 的使命，是让这些能力能够被统一组织、自由组合并共同发挥作用。

让一个人可以站在全球开放科研生态的基础上探索科学问题。

让优秀科研软件能够被更多人真正使用。

让研究不再被工具、环境、学科边界和重复工程工作过度限制。

**OpenLab 不追求拥有全部科研能力，而追求让全球开放的科研能力可以协同工作。**
